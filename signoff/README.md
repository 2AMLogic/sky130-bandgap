# T1 signoff — the graded verdict of record

This block's position on the klayout-tools **design-evidence ladder** is not
prose in this file, in the top-level `README.md`, or in
`design/block-characterization-report.md`. It is
[`block-manifest.json`](block-manifest.json) — what this block claims, and the
evidence envelope backing each claim — graded mechanically by `klt signoff
--manifest`, with the graded output committed under [`reports/`](reports/) as
append-only evidence.

**Read the newest record in `reports/` for the current per-item verdict.**
Nothing here restates the met/unmet count, on purpose: a hand-maintained
checklist goes stale the moment either the evidence or the checklist moves, and
both move. (The checklist grew an eleventh item — power delivery (structural) —
on 2026-09-17, 2AMLogic/klayout-tools#2025, which invalidated this repo's
previous hand-read "5/10" at a stroke.) This file explains *why* each row reads
the way it does and carries the disclosures the grader does not enforce.

```bash
bash signoff/regenerate.sh --dry-run          # render the report, write nothing
bash signoff/regenerate.sh                    # mint a new record under reports/
KLT_SIGNOFF_CMD=klt bash signoff/regenerate.sh  # same, with a klt already at the pin
python3 signoff/check_signoff.py              # offline: pins + record consistency
python3 signoff/check_signoff.py --run-klt    # + `klt signoff --check` vs the record
```

`klt signoff --manifest` exits **3** when the block is not yet T1 and **0**
only at full T1 — both mean the report rendered. The scripts above encode that
distinction. `--run-klt` uses `klt signoff --manifest ... --check <record>`
(klayout-tools#2249), which re-grades and diffs every field except the `build`
block, exiting 0 on `match` and 3 on `drifted`.

- **Checklist** (item skeleton, parsed at run time):
  `klayout-tools/docs/design-evidence-tiers.md`
- **Grader contract** (manifest shape, reasons, what is and is not graded):
  `klayout-tools/docs/cli/signoff.md`
- **Grader revision**: pinned in [`klt-pin.txt`](klt-pin.txt). Deliberately
  separate from `layout/requirements.txt`, which pins the klt build that
  *produced* the DRC/LVS/extract evidence.
- **Pattern**: ported from 2AMLogic/gf180-bandgap's `signoff/` harness (per
  `CLAUDE.md`), with the re-grade switched to `klt signoff --check`.

## Block kind: `analog`

Confirmed against the block, not taken from the issue: every device in
`design/*.sch` is a `sky130_fd_pr` primitive (MOSFETs, `pnp_05v5`,
`res_high_po`) hand-captured in xschem; there is no RTL, no standard cell, no
synthesized netlist. The trim network is magnitude-only resistor segmentation
(DR-002), not a digital partition. The routed layout
(`layout/bandgap-core/reports/<stamp>/bandgap_core_routed.gds`) is generated by
`layout/bin/run-bandgap-routed-flow.sh`, not P&R output, and its extraction
counts only `nfet`/`pfet`/`pnp`/`res_high_po` devices. So this is a
single-kind `analog` manifest (Analog column of items 1, 2, 5, 7 and 11), with
no partition boundary to declare.

Consequence worth stating: for an analog block, **item 7 accepts a `klt pex`
report and nothing else**. The extracted-netlist re-runs under
`sim/*-post-layout/` do not satisfy it.

## What the manifest cites, and what it deliberately does not

Three items are cited: **3** (DRC), **4** (LVS) and **8** (characterization
report). Every citation pins a `content_hash`. Everything else is uncited and
renders `no_evidence` — an accurate statement that no `klt`-gradable check
backs that claim in this repo yet, not a placeholder.

**Items 1, 2, 9 and 10 are uncited on purpose.** They have no `klt` verb
behind them, so the grader scores them on "some passing envelope was cited at
all", never on topical relevance — citing the DRC report for "Repo hygiene"
would render `MET` and the tool would have no basis to object. This repo does
have the artifacts those items describe (xschem schematics + the derived
`layout/bandgap-core/reference.spice`; a committed, script-generated GDS; the
`sim/` corner-run testbenches with a documented reproduction path
(`sim/README.md`) and a pinned PDK in `sim/pdk.json`; a README, license and CI), but asserting them
through an unrelated citation would make the record say something no tool
checked. `klayout-tools/docs/cli/signoff.md` ("Items 1, 2, 9, and 10")
recommends exactly this default, and the fleet roll-up steps over these four
when naming a blocker.

**Items 5 and 6 are uncited because this repo's evidence is not in a gradable
shape.** `sim/*/records/*.json` use this repo's own corner-run record schema
(`record_id`/`matrix`/`corners`/…), not `klt sim` / `klt yield` envelopes, and
items 5 and 6 accept only those kinds. Separately — and this would not go away
with a format translation — item 5 has a substantive gap: the box-method
temperature-coefficient row fails at every corner (schematic and post-layout),
and startup time fails at the fastest process corners; see the scoreboard in
[`design/block-characterization-report.md`](../design/block-characterization-report.md)
§2 and [DR-009](../spec/decision-records/DR-009-tc-floor-disposition-defer-curvature-correction.md).
Item 6's substance exists (`sim/monte-carlo-untrimmed/`, N=300 per
temperature, current against the post-#193 design) but not as a `klt yield`
report.

**Item 7 is uncited because this repo has produced no `klt pex` report.** The
post-layout suites under `sim/*-post-layout/` re-run every bench on the `klt
extract --parasitics` netlist, but that is not the artifact item 7 accepts.
Because no `pex` report exists there is no `body_bias` block to read, so this
claim makes **no statement** about whether post-layout numbers were measured on
a properly body-biased extracted netlist. (For what it is worth, the cited
`extract.json`'s own `unbiased_pmos_body_nets` is empty — but that is a
different field from a different verb, and `klt signoff` does not read it.)

**Item 11 (power delivery, structural) is uncited** because this repo has no
`klt erc` supply spec or report. It still has a row — `klt signoff` renders
every item the pinned checklist lists, so item 11 shows `unmet` /
`no_evidence` in the committed record. Tracked in #281.

## Disclosures that travel with the claim (claimant-enforced, not graded)

### Item 3 — DRC coverage

`klt signoff` grades item 3 on `status: "clean"` alone; a `met` verdict is
**not** evidence that the deck's gaps were disclosed, so they are disclosed
here, quoted from the cited envelope's own `coverage` block
(`layout/bandgap-core/reports/20260817-020222-13476b7/drc.json`, echoed in the
committed record's `citation.coverage`):

- `layers_in_stream_without_rules` (8) — layers drawn in this stream the deck
  has no rule for: `64/20`, `65/44`, `66/13`, `68/5`, `82/44`, `83/20`,
  `86/20`, `94/20`.
- `rules_skipped` (0) — none.
- `deck_scope` — **not reported.** The envelope was produced by `klt` 0.2.0,
  which predates the `deck_scope` field, so the record shows it empty. That is
  "this artifact reported no scope", not "the deck covers everything". What the
  envelope *does* state is the deck's checked layers: `65/20`, `66/20`, `66/44`,
  `67/20`, `67/44`, `68/20`, `68/44`, `69/20` (diff, poly, licon, li, mcon,
  met1, via, met2) — "clean" means clean on those layers only. Per
  `design-evidence-tiers.md`, a claim that never states its `deck_scope` has
  not fully satisfied item 3's disclosure requirement however clean the status
  is; closing that needs a DRC re-run on a `klt` that reports it.
- The met2 minimum-area rule (`m2.6`) is outside the curated deck and is
  covered only by this repo's own `met2-drc.json` checker, which is not a `klt
  drc` envelope and is not cited.
- `input_verified` is `null`: the envelope's `file` is an absolute path in the
  worktree that produced it, so `klt signoff` cannot re-hash the GDS
  (filed generically as 2AMLogic/klayout-tools#2340). `check_signoff.py`
  re-hashes it instead — see below.

### Item 4 — why a `match` renders `unmet`

The cited envelope (`.../20260817-020222-13476b7/lvs.combined.json`) reports
`status: "match"`, engine `klayout`, 11/11 nets and 16/16 devices matched,
`mismatch_count: 0` — and item 4 still renders `unmet` with `reason:
"unverifiable_provenance"`. That is correct:

- The envelope was produced by `klt` 0.2.0, which left `provenance.input`
  `null`. The grader's freshness gate reads exactly that field, so a pinned
  `content_hash` has nothing to match and the citation cannot be proven fresh
  **by the grader**.
- The run *was* in fact made against the committed extracted netlist: the same
  envelope's `environment.layout_sha256` is
  `c77289bf…deb709dad`, the hash of the committed
  `bandgap_core_routed.extract.spice` (and the pin `check_signoff.py`
  re-verifies). But a field the grader does not read is not evidence the
  grader can use, and dropping the pin to force a `met` would assert freshness
  no tool checked. The pin stays; the row stays `unmet` until LVS is re-run on
  a `klt` that records `provenance.input`.
- Independent of freshness: this is a **pre-extracted-netlist** compare with
  `combine_devices: true` (see `lvs.combined.request.json`), single engine
  only; the envelope carries no `power_connectivity` or `body_verification`
  block (both predate 0.2.0), so neither was checked. The uncombined
  `lvs.json` beside it reports `mismatch`; the combined compare is the one
  the characterization report cites, and `layout/README.md` / DR-003 explain
  why `combine_devices` is the physically correct accounting here.

### Item 8 — what the generic envelope asserts

[`characterization-evidence.json`](characterization-evidence.json) is a
hand-rolled `"kind": "generic"` wrapper — the only kind item 8 accepts — around
[`design/block-characterization-report.md`](../design/block-characterization-report.md).
Its `status: "pass"` asserts **only** that item 8's artifact exists and is
current: one aggregated block-level report naming the evidence record behind
every ratified spec row, regenerated at `e8e2e46` with no newer `sim/` or
`layout/` record on disk. It does **not** assert the block meets its spec —
that report itself records the TC row as FAIL at every corner, startup time as
FAIL at fast corners, and trim as STALE. The envelope pins the report's
sha256; editing the report without re-pinning fails `check_signoff.py`.

## How this is kept from rotting

`klt signoff` compares a manifest pin against the *cited envelope's own*
recorded input hash. For all three citations here it cannot also re-hash the
artifact (`input_verified: null` — see items 3/4/8 above), so a pin could go
stale in a way the grader cannot see. [`pinned-inputs.json`](pinned-inputs.json)
names the committed artifact behind every pin, and `check_signoff.py`
re-hashes it.

| Check | Where | Needs |
|---|---|---|
| Manifest shape (`block`, `kind`, every citation pins a `content_hash`), pins vs. committed artifacts, record consistency | `checks` job, `npm run check:signoff` | python3 only |
| `klt signoff --manifest ... --check <newest record>` at the pinned revision | `signoff` job | network (installs klt at `klt-pin.txt`) |

So a manifest citing an artifact that has since changed, a record that no
longer reproduces, a pinned checklist that moved, and a mis-keyed evidence
entry that `klt` would silently ignore all fail CI instead of rotting.

When evidence legitimately changes (a new layout report, a regenerated
characterization report): re-point the manifest and `pinned-inputs.json`,
re-pin, run `signoff/regenerate.sh` to mint a new record (never edit an old
one), and update the disclosures above if the cited envelopes' `coverage` or
provenance moved.
